# 存储维护恢复契约

更新：2026-09-05。对应 V2-06A 首个子包，管理库 V29／V30。范围为 Paimon Compact、快照过期和孤立文件清理共用的维护协调链路；真实故障演练使用专用表的 Compact。持续任务及周期 attempt 的持久化 Gateway 恢复仍待开发。

## 操作与环境

新增请求固定逻辑 assetId、原 Catalog／库／表、发起人、SQL、Gateway／Flink 地址、非敏感 Paimon 环境及随机关联标识，记录 `bound_v1`。凭证不进入日志或事件；Catalog 初始化时仅在非敏感环境仍一致的条件下解析当前密码。初始化完成后使用原会话，修改运行配置或关闭新提交不停止旧操作观测及清理。

执行阶段为 `SESSION → SESSION_READY → CATALOG → USE → CALL → JOB（如有）`。每个外部提交先在独立事务提交意图，再执行一次 POST，随后记录返回句柄。每表数据库锁串行化发起、定时协调和人工处置；V30 所有权令牌阻止旧协调器在接管后回写。线程内最多两个协调调用，为独立事务保留连接池空间。该实现没有完成整个应用的多副本认证。

有原句柄时，在原地址续查；缺少句柄时保留 `unknown`，不重复 POST。超过观测时限记录 `timed_out` 并继续核验，不能当作执行失败后重新提交。原操作明确 ERROR／CANCELED 记录失败；CALL 的完整同步结果或所关联 Job 的明确终态用于确认结果。CLOSED、地址不可达、未知状态均不推断成功。同表存在 pending／running／unknown／timed_out 时拒绝新维护。

依据 [Flink 2.2 SQL Gateway REST 文档](https://nightlies.apache.org/flink/flink-docs-release-2.2/docs/dev/table/sql-gateway/rest/)，操作状态接口只提供状态，没有供任意人工句柄证明原 SQL 的关联信息。因此界面不开放输入任意 Operation ID 来认定业务结果；Job 接管必须核验原 Flink 返回的 Job ID 和随机关联名称。

## 执行与清理分离

执行结果确认后独立登记会话清理意图、尝试次数、下次时间及错误。失败按 5 秒起步、最大 300 秒退避重试，进程重启后继续。DELETE 仅调用原 Gateway，明确删除成功或包含原会话身份的不存在响应才能确认；代理通用 404 不能作为证据。清理失败不覆盖已确认的执行结果和完成时间。

结果未知的 CALL 不关闭会话；无 Session 句柄的准备请求取消后标记清理证据缺失。无法定位的遗留会话需要在原引擎核对，平台不能保证自动回收。

## 恢复接口与页面

入口：**数据资产 → 存储维护 → 维护操作日志 → 证据与处置**（路径 `/dwh/maintenance`）。列表按类型和状态筛选；详情展示原目标、端点、阶段、句柄、清理计划、SQL 及最近 200 条只追加的恢复事件。页面兼容后端日期字符串和日期数组。

- `GET /dwh/maintenance/{id}`：操作快照及恢复事件。
- `POST /dwh/maintenance/{id}/recovery`：必填 `expectedRevision`、`action`、`reason`（非空且最多 1000 字）；关联 Job 时填 32 位十六进制 `jobId`。
- `GET /dwh/maintenance/logs`：保留原列表接口，按固定历史目标鉴权，支持 `tableMetaId`、`operation`、`status`。

| 动作 | 条件与效果 |
| --- | --- |
| observe | 在绑定环境重验并续查，不重发缺句柄步骤 |
| retry_cleanup | 已确认执行终态且待清理时立即重试；保留原执行结果 |
| attach_job | 仅 CALL 结果未确认且尚无 Job；原 Flink 返回的 ID 与关联名称都一致才绑定 |
| cancel_preparation | 仅业务 CALL 提交意图尚未记录的准备阶段；标记取消并清理已知会话 |
| cancel_pending | pending 且没有 Session／Operation／Job，取消平台尚未提交的请求；不推断平台外执行结果 |
| note | 补充原因和处置记录，不改变检测到的执行结果 |

修订冲突返回 409，用户刷新证据后重新判断；不以自动重试覆盖用户看到的状态。服务端强制检查条件，页面隐藏不适用动作。没有强制成功、清空未知或重新执行入口。

读取需要查看权限及原目标范围；处置需要当前有效账号和维护权限。继续提交新 SQL 前重验原发起人的有效状态、权限和原资产绑定。撤权后仍可只读观测及清理已结束会话。非管理员无法用当前改绑后的资产权限获取旧目标的历史；管理员可以核对未绑定的历史记录。

## 升级、恢复与边界

V29 增加环境、观测、清理字段及协调／事件表；V30 增加协调所有权令牌。不改写旧句柄、目标、状态、执行人或环境，旧记录为 `legacy_unbound`，不自动续查。升级前本地 44 条 pending 和 2 条 success 均保留；未提交且无句柄的 pending 可由管理员取消，其他历史不具备的关联证据仍明确缺失。

升级前备份为本地忽略目录 `tmp/backups/pre-v29-local.sql`（0600）。部署时停止旧程序写入，由单控制面执行迁移并使用配套前端。禁止将旧后端与新协调器混跑；旧程序不理解意图、清理和令牌约束。没有自动降级迁移，故障优先前向修复；需恢复备份时先停写并核对外部在途作业，管理库恢复不能撤销已经发生的 Compact 或清理。完整备份恢复仍由 V2-11B 验收。

真实证据见 [恢复故障演练](validation/v29-maintenance-recovery-smoke.json) 与 [验收基线](v2.0-acceptance-baseline.md)。脚本通过本地代理丢弃真实已受理响应、改变运行地址、重启后端容器，并核对最终 SUM 未改变；测试使用精确名称与 ID 清理，不删除既有业务记录。

尚未认证的范围：持续部署／周期 attempt 的完整持久化会话恢复；双后端及数据库连接失效接管的真实故障演练；原生 Paimon Job 保留关联名称的正向人工接管（目前仅单测）；结果分页／多 Job 的扩展适配；生命周期策略、Tag 引用保护及删除后的恢复。共享 Gateway 传输已供任务提交复用，但不等于这些恢复能力完成。
