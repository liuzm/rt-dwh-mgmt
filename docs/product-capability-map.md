更新日期：2026-09-05。计划起点：`0046f3c`；当前包含工作区 V2-10A／V2-09A 及 V2-06A 存储维护子包改动，数据库 V30，沿用 V27 窗口质量能力。

本文回答“产品面向谁、能完成什么、哪些能力仍需补齐”。当前状态以代码、[实施进度与验收记录](v2.0-implementation-progress.md)为依据；[2.0 迭代规划](v2.0-product-iteration-plan.md)用于定义目标范围，不能直接作为完成清单。最初梳理采用静态核对，随后已随 V28 实施更新实际测试证据。

## 1. 产品定位与用户价值

**RT-DWH 是面向数据工程团队的实时湖仓开发与可信数据交付平台。** 平台在 Flink、Paimon、Doris 之上，统一数据接入、开发发布、调度交付、资产治理、质量检测和数据消费。

当前主链路为：业务数据库 → Flink CDC／SQL → Paimon 分层资产 → Doris 查询 → 报表／数据 API。任务发布版本、业务日期、具体产出和质量证据共同解释一批数据是否可交付。

| 使用者 | 主要问题 | 当前产品价值 |
| --- | --- | --- |
| 数据工程师 | 如何接入业务库、加工数据、部署任务及恢复故障 | 统一数据源与开发入口，持续任务和周期任务分别管理 |
| 数据开发与分析师 | 数据在哪里、含义是什么、是否可靠、如何复用 | 资产检索、结构与业务说明、质量证据、SQL、View 和报表 |
| 数据治理与运维人员 | 哪批数据异常、影响谁、运行是否正常 | 交付状态、规则与窗口检测、上下游关系、告警和维护记录 |
| 应用开发者 | 如何通过受控接口获取数据 | 参数化数据 API、应用凭证、服务授权和调用记录 |
| 平台管理员 | 如何管理多人协作、权限和环境 | 用户角色、表级数据范围、环境配置与操作审计 |

以上是业务分工，不等同于系统内置角色或已提供独立门户。适用重点是中小型数据团队的实时数仓建设和开发验证；生产支持范围需要专项验收确认。

## 4. 数据质量：当前覆盖与下一步

质量能力已经从“跑一次规则看通过率”扩展为“按业务窗口检测，并为交付留下证据”。目前支持的质量维度需要明确区分：

| 维度 | 当前规则或能力 | 还缺什么 |
| --- | --- | --- |
| 字段完整性 | 空值率阈值 | 跨字段完整性、关键字段模板与画像建议 |
| 唯一性 | 单字段非空去重数与总行数的比例 | 复合主键、多字段唯一和重复明细定位 |
| 有效性 | 表达式越界率；表达式结果为 NULL 默认视为无效 | 枚举、正则等易配置模板 |
| 数据规模 | 行数下限 | 波动基线、同期环比与异常检测；当前规则名中的 compare 不代表已提供跨表对账 |
| 时效性 | 业务日期窗口、产出时间、基础 SLA 风险概览 | 截止时间、时区、宽限期、迟到与恢复事件、按时且通过的交付率 |
| 一致性与准确性 | 可用现有约束表达部分业务校验 | 跨表对账、引用完整性、权威源核对与准确性规则体系 |

检测流程为：选择资产 → 配置规则与范围 → 预览 SQL → 手动／定时／产出触发 → 保存检测证据 → 按窗口形成异常 → 修复数据并重检。

当前证据包含目标表、规则版本、业务窗口、检测 SQL、检测行数、异常计数、实际指标、结果及错误。产出触发使用任务发布时冻结的规则；修改当前规则后，要重新发布任务才能改变后续交付契约。按原规则重检复用原产出并追加证据，不把重检时间改成新产出时间。

产品解释需保持以下边界：

- **全表通过不能证明某日数据完整。** 日窗口规则按选定时间字段筛选；时间字段为 NULL 的行需要另配全表空值检查。当前未固定 Paimon 物理快照，重检会读到后续写入的数据。
- **人工确认不等于检测通过。** 确认仅改变异常处置状态；某日检测通过不会恢复另一日异常。门禁仍按真实检测结果判断。
- **异常计数需要按规则解读。** 唯一率计数为总行数减非空去重数；行数下限没有对应的行级异常计数。
- **质量通知处置尚未完整。** 平台运行告警已有渠道与恢复机制，质量工作台仍需补负责人、工单、备注、通知路由和超时升级。
- **SQL 预览用于确认规则。** 它不执行检测，也不等同于完整的字段存在性验证或执行计划检查；当前未提供任意自定义 SQL 质量规则。

详细配置及验收契约见 [数据质量能力规划](data-quality-capability-plan.md)。

## 5. 三条典型业务流程

### 实时数据接入与分析

数据工程师创建 MySQL／PostgreSQL 连接，选择源表并确认 Paimon 映射；预览 CDC SQL，发布并启动持续任务；通过任务指标确认写入后，在资产目录补充说明与负责人；分析师从资产进入 SQL 查询，进一步制作报表或数据 API。PostgreSQL 的完整类型兼容仍需按实际源表验证。

### 周期交付、质量阻断与补数

开发者定义周期 SQL、产出表、依赖、参数与质量规则后发布，配置 Cron 或发起指定日期补数。运行实例绑定发布版本和日窗口；计算成功后检查质量，产出可用才释放对应的数据依赖。异常修复后按原规则重检。补数默认重建本批次的上游链路，显式选择复用时才使用匹配版本和窗口的已有可用产出。

纯控制依赖可显式按“执行成功”放行。确定未提交的失败尝试可重试；提交结果不明时保留未知状态，当前没有通用的自动重放保证。

### 资产复用与异常追溯

用户检索资产并查看结构、负责人、任务来源、质量记录及消费关系；把可复用 SQL 发布为受管普通 View，供查询、报表和 API 使用。底层权限撤销、对象缺失或定义漂移会阻断相应受管 View 消费；排查可回到资产和发布上下文。全量变更影响评估、输出契约迁移及异常工单还需后续建设。

## 6. 后续产品优先级建议

以下为根据当前能力差距提出的排序建议，不是新增的已承诺排期；继续使用原 V2 工作包跟踪。

这些差距已拆解为 [未完成能力与优化开发计划](v2.0-remaining-development-plan.md)，按 2.0 收尾、2.1 优化、Beta 与后续扩展分别安排，并明确前置依赖和验收标准。

| 优先级 | 建议工作 | 对应工作包 | 用户可验收的结果 |
| --- | --- | --- | --- |
| P0，消费发布可靠性 | API 发布隔离已实现，补齐页面验收；继续开发可用产出消费策略 | V2-09A/B | 编辑草稿不改变线上返回；发布与回退有明确版本；约定只消费可用产出的入口遵守门禁 |
| P0，生产运维可靠性 | 运维及伸缩操作协调、未知提交接管、跨副本互斥；升级与故障恢复演练 | V2-06、11 | 重启、断连或重复请求不产生重复写入／维护；最终状态可核验，失败有可执行的恢复路径 |
| P1，质量交付闭环 | SLA 事件与窗口交付看板 → 负责人和通知 → 审批豁免 | V2-08 后续 | 能回答哪批迟到、质量是否通过、谁负责、何时恢复；确认与豁免分别留证据 |
| P1，资产安全演进 | View 影响评估与迁移、失效扫描；物理身份重绑定；存储策略、Tag 与恢复验证 | V2-04、05、07 | 变更前可识别受影响消费方，变更后有迁移和恢复手段 |
| P1，易用性与规模化 | 质量模板与画像、每规则调度和执行预算、历史分页；跨页筛选和多尺寸回归 | V2-08、10、11 | 常见检查无需手写表达式；大表检测有资源约束；返回列表不丢上下文 |
| Beta，能力扩展 | 原生物化适配、策略自动伸缩；后续再评估 Kafka、文件入湖、列级治理和指标语义层 | V2-12 及后续路线图 | 每类能力独立验证生命周期、权限及恢复后开放 |

原生物化入口已在 V2-10A 标记“实验能力 · 未开放”并禁止选择，后端同步拒绝对应新建／发布请求。Flink 原生 Materialized Table 的刷新与恢复闭环尚未认证，继续按 Beta 范围推进；本次已通过浏览器核对不可选状态及实验标记。

当前阶段可表述为：**实时湖仓主链路与 2.0 可信交付核心已落地，质量治理和生产运维仍在补齐。**
