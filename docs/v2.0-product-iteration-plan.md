## 1. 版本结论

建议将下一大版本定义为 **RT-DWH 2.0：可信湖仓交付**。

当前版本已经有接入、任务、资产、质量、查询、报表、API 和运维入口。主要问题从“有没有功能”转为“这些功能是否围绕同一份定义、同一批数据、同一个交付结果工作”。2.0 应从管理工具集合，升级为以数据资产为中心的开发与交付平台。

本版本只承诺五个用户结果：

1. **接得稳**：接入前知道配置是否可运行，异常后知道如何恢复，Schema 变更不会悄悄破坏下游。
2. **交得准**：发布内容可复现，执行成功与数据可用分别判断，失败门禁能够阻断依赖交付。
3. **找得到、用得明白**：表、视图、产出、负责人、质量、新鲜度和消费关系在一个资产详情中解释清楚。
4. **管得住**：运维动作有预检、执行记录、真实终态和安全边界，伸缩“已受理”不被误报为“已完成”。
5. **操作连续**：页面紧凑、状态稳定，从异常进入诊断再返回列表不丢筛选、日期和上下文。

不把 Kafka、全新计算引擎、完整指标平台、多租户、通用 BI 同时塞进本次 GA。物化能力分类型、分成熟度开放，不再用一个“物化任务”入口覆盖所有语义。

## 2. 当前产品逻辑与主要缺口

### 2.1 已有基础应保留，不重建

- 写入链路：业务源 → Flink CDC／SQL → 平台 Paimon Catalog 与 Warehouse。
- 查询链路：Doris External Catalog → 即席查询／报表／数据服务。
- 执行模型：持续任务与周期任务已分离；周期实例已绑定任务定义版本。
- 治理基础：质量规则和检测记录、产出状态、表级血缘、RBAC、数据范围、审计与告警已有代码。
- 运维基础：Savepoint、Job 状态校准、受保护的并行度调整、集群容量展示和部署模板已有实现。
- UI 基础：已做全局紧凑样式和路由骨架，下一步应补交互一致性与回归，而非再次全量重写页面。

### 2.2 本次核对发现的交付风险

下表“代码事实”是静态观察；“影响”是据此推导的产品风险，仍需用例复现和真实引擎验证。

| 编号 | 代码事实 | 产品影响与下一步 |
|---|---|---|
| R01 | `WorkflowService.complete` 先把实例记为 success，再登记产出；依赖释放只检查同业务日期存在成功实例 | 产出 blocked 不阻止成功条件依赖；必须区分计算完成与交付可用 |
| R02 | 发布快照序列化 `SyncTask`；产出和依赖执行时分别读取当前配置 | SQL 已冻结，但交付契约未整体冻结；在途实例可能受后续产出／依赖编辑影响 |
| R03 | 依赖选择同业务日期任一成功上游，不固定批次或具体产出版本 | 历史成功可能满足新补数依赖；要明确“复用已有可用产出”和“本批重算”的不同语义 |
| R04 | `DwhMetaService` 单独按 `sessionId/operationId` 提交 CALL；任务提交已经使用 `sessionHandle/operationHandle`，维护路径未等待终态就清理会话 | 维护页不能把请求提交视为执行成功；统一 Gateway 客户端并补状态协调 |
| R05 | 物化场景标为 available，走通用 SQL→单 Job ID 模型；部署未配置原生物化所需的 Catalog Store／刷新调度 | 不能据入口判断原生物化表已完整支持；改为能力预检与实验开关 |
| R06 | 血缘图入口只有接口权限，服务全量读取任务、表、数据源，未接入当前用户数据范围 | 元数据可能跨范围暴露；发布前补对象级授权和负向用例，不能只保护查询结果 |
| R07 | 数据服务修改直接更新被调用的定义，`apiVersion` 自增但无不可变发布快照；列表／授权管理主要依赖接口权限 | 编辑与线上版本未隔离；需要发布指针、版本契约和资源归属校验 |
| R08 | API 限流、查询运行句柄／并发额度在进程内；Quartz 未显式配置集群模式；Runner 默认固定 executorId | 多副本下额度、取消、任务协调需要专门设计与验收，Helm 可渲染不等于 HA |
| R09 | Paimon 资产实体以 db+table 定位，无视图类型；血缘 SQL 使用 FROM/JOIN/INSERT 正则提取 | 引入视图前要补对象身份、类型和依赖解析；现有血缘不能承担完整 SQL 安全分析 |
| R10 | 部分状态接口把缺失 Lag／吞吐返回 0；前端没有独立测试脚本 | “无数据”可能被理解为“健康”；增加未知／过期状态与浏览器回归 |

证据入口见第 13 节。R01、R04、R06 等当前交付问题可先作为 1.x 修复发布，不应为了凑大版本而延后。

## 3. 统一产品模型

### 3.1 三条用户主线

| 主线 | 用户步骤 | 完成标志 |
|---|---|---|
| 实时接入与加工 | 配置源 → 预检 → 表映射／SQL → 发布部署 → 持续运行 → 观察新鲜度 → 恢复或变更 | 数据持续可见，关联部署版本、源位点／Checkpoint 和目标资产 |
| 周期交付 | 定义加工 → 声明输入输出与质量契约 → 发布 → 调度／补数 → 计算 → 检测 → 交付 | 指定业务窗口产出 available，满足声明的下游依赖 |
| 数据消费 | 搜索资产 → 理解口径和可用窗口 → 验证 SQL／视图 → 发布报表或 API → 消费与追踪 | 消费的是明确版本和新鲜度策略下的数据，而不只是“SQL 执行成功” |

质量、血缘、审计和运维作为以上三条主线的共享能力，不再要求用户在多个治理首页中自行拼接上下文。

### 3.2 对象边界

| 对象 | 负责什么 | 不等于什么 |
|---|---|---|
| 数据源连接 | 业务源地址、凭证、连通性、采集权限 | 平台 Paimon 存储配置 |
| 运行环境 | Gateway、Flink、Doris、Catalog、共享存储和能力清单 | 自动创建一整套基础设施 |
| 任务定义／发布版本 | SQL、参数契约、模式、输入输出、依赖、门禁、运行配置引用 | 某次 Flink Job |
| 部署修订 | 某个持续任务实际运行的发布版本、Job、恢复点与运行配置 | 周期任务业务日期实例 |
| 运行实例／执行尝试 | 某业务窗口的一次逻辑运行，以及重试的执行过程 | 最终可信数据产出 |
| 数据产出 | 资产、业务窗口、物理数据引用、质量证据、交付状态 | 表是否存在 |
| 统一资产 | 稳定 ID、类型、物理位置、Schema、责任人、上下游 | 每个模块复制一份表名 |
| 数据服务发布版本 | SQL／视图引用、参数和输出契约、权限、可用性策略 | 草稿内容或自增版本数字 |
| 运维操作 | 一个可追踪的维护、恢复、扩缩容或部署动作 | HTTP 200／操作已受理 |

建议资产采用稳定 `assetId`，物理定位单独保存环境、引擎、Catalog、Database、Object；第一版仍然是一套部署对应一套平台 Paimon Catalog／Warehouse。这个设计为对象类型留扩展点，不意味着 2.0 同时建设多湖仓或多租户。

### 3.3 必须统一的状态语义

| 维度 | 建议状态／规则 |
|---|---|
| 定义 | draft → validated → published → archived；编辑产生新草稿，不覆盖已发布版本 |
| 持续部署 | deploying／running／degraded／suspended／failed／stopped；保存期望状态与引擎观测状态 |
| 周期执行 | waiting／queued／running／succeeded／failed／cancelled；每次重试有独立 attempt 和引擎关联 |
| 数据交付 | pending → checking → available 或 blocked；过期新鲜度作为独立 freshness 状态，不覆写历史检测事实 |
| 运维操作 | requested → accepted → applying → succeeded／failed／timed_out；状态未知时保留 unknown，不猜测成功 |
| 监控数据 | observed／unknown／stale；没有采集值不能显示为 0 ms 或“运行正常” |

这些是目标语义，不要求第一步重命名所有数据库枚举。先增加必要字段和 API 映射，兼容现有客户端，再按迁移计划收敛。

## 4. 优先做对“发布与交付”

### 4.1 发布的是完整契约

发布包至少固定：任务定义版本、执行模式、类型化参数定义、输入输出声明、依赖绑定策略、质量规则版本／门禁策略、SLA 口径、执行配置引用与摘要。

- 持续任务也需要发布版本和部署修订，不能只有“编辑配置然后重启”。
- 产出配置、规则和依赖修改后，必须重新发布才能影响新实例；旧实例继续使用旧契约。
- Cron、时区和业务日期偏移保留独立调度修订；实例记录触发时的调度修订，不因调度编辑改变历史。
- 环境配置记录版本和非敏感指纹；凭证只保存受控引用，执行时解析，不把明文密钥冻结到快照。
- 运行权限在提交／消费时重新检查；版本不可变不能成为保留已撤销权限的理由。
- 任务配置回滚、Flink 状态恢复、Paimon 数据回退是三种不同动作，分别预检与审计，不提供含糊的“一键全回滚”。

### 4.2 质量门禁真正控制交付

- 对声明数据依赖的下游，以对应资产、业务窗口和绑定产出的 available 为放行条件；纯控制依赖可显式选择 execution_success。
- 普通调度默认绑定符合契约的最近可用上游产出；补数默认使用本批产出，显式允许时才复用历史结果，并保存具体 productionId。
- 检测范围绑定本次分区／业务窗口；不再仅以“整张表当前规则通过”证明某次补数质量。
- 规则不通过与引擎查询失败分别显示；无匹配规则且启用严格门禁时 fail-closed，并明确显示“未配置门禁规则”。
- 检测与发布设计为可恢复步骤，重复回调／重试不会重复登记；质量结果与产出保留相互引用。
- 人工豁免必须有权限、理由、到期时间和审计；豁免不改写原始检测失败记录。

### 4.3 明确“阻断”的范围

当前 blocked 只是管理库标记，无法撤回已经写入 Paimon 的内容。2.0 的最低保证是：阻断声明依赖和受治理的报表／API 交付，并在即席查询中明确提示资产质量状态。

需要“消费者绝不读到未通过数据”的强隔离场景，采用经验证的暂存产出加受控发布引用：检测固定物理版本，再切换消费引用；没有引擎级快照固定／隔离能力时，不对任意直查 SQL 承诺强隔离。持续 Upsert 表尤其不能用一个 available 布尔值代表永久通过。

## 5. 资产、View 与物化的产品方案

### 5.1 资产详情成为核心工作台

统一详情页组织为：概览、字段与契约、生产任务、产出记录、质量、新鲜度、上下游、生命周期、变更记录。用户从一个资产可以进入源任务、检测批次、查询、报表和服务，返回时保留上下文。

- Schema 变更按兼容新增、风险变更、破坏性变更分类；重命名／删列／类型收窄先评估下游影响。
- “整库同步”首版明确是当前表清单快照；自动发现新增表属于独立策略，不能默认承诺自动跟随。
- ODS 当前态主键表与历史变更日志要明确区分；普通主键 Upsert 表不等于永久保存所有历史变更，也不天然满足长期重放。
- 血缘先完善可验证的表级解析、视图展开和发布版本关联；列级自动血缘放到后续。

### 5.2 三类对象不能混淆

| 对象 | 产品用途 | 2.0 建议范围 | 必要边界 |
|---|---|---|---|
| 普通 SQL View | 复用查询定义和简化消费入口 | GA：优先实现 Doris 侧受管视图 | 不存结果；需依赖解析、发布版本、失效检测和权限校验 |
| Flink Materialized Table | 由刷新任务维护 Paimon 中的加工结果 | Beta：先验证持续刷新闭环；FULL 刷新通过专项验收再开放 | 管理表定义、刷新任务与生命周期，不等于普通 SQL 单 Job 提交 |
| Doris 异步物化视图 | 在查询引擎侧保存结果以加速访问 | 2.1 候选；2.0 只做兼容性验证，不作为 GA 必交 | 有额外存储和刷新成本，需显式约定新鲜度，不默认自动重写所有查询 |

普通 View 基于 Doris 的原生建视图能力建设专用受控 DDL 通道，即席查询仍保持只读；不能简单放开 SQL 工作台的 CREATE／DROP。Doris 提供视图定义能力，具体跨 Catalog 语句、权限与当前镜像组合进入兼容测试。[Doris CREATE VIEW](https://doris.apache.org/docs/4.x/sql-manual/sql-statements/table-and-view/view/CREATE-VIEW/)

Flink 原生物化表需要 SQL Gateway、支持的 Catalog、Catalog Store，以及 FULL 刷新相关的调度配置；具备普通 Gateway 并不自动满足这些条件。RT-DWH 的周期 SQL 调度与引擎原生物化刷新必须选定唯一调度所有者，不得重复触发同一个结果表。[Flink 2.2 物化表部署](https://nightlies.apache.org/flink/flink-docs-release-2.2/docs/dev/table/materialized-table/deployment/)

Doris 4.x 文档将异步物化视图定义为最终一致的内部物化结果，并列出 Paimon 全量／分区刷新支持及自动触发限制。因此“支持 Paimon 物化查询加速”仍需绑定实际版本、刷新策略与查询计划验收，不能等同于实时一致。[Doris 异步物化视图](https://doris.apache.org/docs/4.x/query-acceleration/materialized-view/async-materialized-view/overview/)

本轮未取得可用的 Paimon 2.0 普通 View 专项页面，不以 master 文档推定当前 JDBC Catalog 与 Doris 的跨引擎 View 兼容性。该方向单独验证，不作为第一阶段依赖。

### 5.3 视图安全准入

- 第一版不把 View 当作提升底表访问权限的捷径：校验 View 及其传递依赖，查询／服务发布都不能仅校验顶层 View 名称。
- 缺失定义、循环依赖、无法安全解析的 SQL 默认拒绝发布；解析结果带来源和可信度，不能以正则血缘代替权限分析。
- Flink 多语句、Doris SQL 分别使用经过测试的方言处理；当前 MySQL AST 校验不能直接假设兼容全部 Flink DDL。
- 更改视图输出列前展示消费方影响；保存 SQL 收藏仍然不是发布 View。

## 6. Paimon 生命周期与 Flink 运维

### 6.1 分层不是四套存储

保持“一个环境一套 Paimon Catalog 与共享 Warehouse”；ODS／DWD／DWS／ADS 是逻辑分层。2.0 增加分层策略模板、表级覆盖、责任人、版本与执行历史，不按层复制集群。

策略拆为四类：Compaction、小文件与写读效率；Snapshot、回溯与读取恢复窗口；Tag、受保护的时间点；Partition、业务数据到期。Snapshot 清理不等同于按业务日期删除数据，过短保留可能影响长查询或流式恢复，应根据实际读写和恢复窗口预检。[Paimon 2.0 快照管理](https://paimon.apache.org/docs/2.0/maintenance/manage-snapshots/)

GA 最小能力：统一维护执行器、真实完成／失败记录、单表／批次日志、手动 Tag 管理、策略预览、Compaction 策略调度。快照／分区／孤立文件的破坏性清理必须显式启用，验证保护窗口后才执行；未知引用、无法判断活跃读取或环境能力不足时阻止自动删除。

不默认给所有层设置同一个保留天数，不把 Tag 当作异地备份，不承诺 Compact 后空间一定立即下降。策略需要展示实际扫描范围与结果；引擎不支持精确 dry-run 时明确标记估算，不能伪造待删除文件清单。

### 6.2 Gateway 和集群的职责

- SQL Gateway 是会话与提交入口，Flink 集群提供 JobManager／TaskManager 执行资源。
- 首版继续支持已有单集群连接方式，新增环境能力预检；不同时自建多集群调度平台。
- Standalone 模式调并行度不代表自动增加机器或 Slot。
- Kubernetes 模式是否能申请 TaskManager，取决于实际调度器、资源管理器、权限与配额，不能仅根据 provider 配置显示“支持自动扩容”。
- 当前仓库示例的 Operator 管理 Session Cluster，Gateway 提交的 Job 不应被宣传成自动进入 Operator 作业级 Autoscaler 管理。

### 6.3 从“调节按钮”到伸缩操作闭环

1. 预检：作业类型、调度器、最大并行度、可用资源、配额、Checkpoint 与恢复存储。
2. 记录：期望并行度、观测并行度、原始配置、操作者、原因、操作 ID。
3. 协调：跟踪资源等待、重调度、运行恢复与后续 Checkpoint；明确可能短暂中断，不称无损热扩容。
4. 失败：容量不足、超时或恢复失败时保留原因，提供经过预检的恢复动作；不无限自动重试。
5. 策略：2.0 GA 先人工决策＋容量建议；基于指标的自动伸缩作为 Beta，具备冷却时间、上下限和人工锁定后再开放。

## 7. 信息架构与紧凑 UI 迭代

| 一级入口 | 核心内容 | 旧入口的处理 |
|---|---|---|
| 工作台 | 我的待办、异常交付、活跃任务、最近资产、全局搜索 | 合并数据总览与公共能力的重复摘要，保留原能力深链 |
| 数据开发 | 业务数据源、持续任务、周期任务、依赖编排、发布记录 | “同步任务”改为覆盖接入与加工的开发入口；任务与运行分开 |
| 数据资产 | Paimon 表、受管 View、物化对象、资产详情与血缘 | 统一身份和详情，不增加多个独立资产目录 |
| 运行中心 | 持续 Job、周期实例、维护操作、伸缩记录、告警与诊断 | 集中运行事实；仍可从任务／资产详情直接进入 |
| 数据消费 | 即席查询、SQL 库、报表、数据 API | 区分 SQL 收藏、视图、报表与已发布接口 |
| 平台管理 | 环境连接、运行策略、用户权限、通知渠道、审计 | 高频运维从设置页移出，基础配置留在这里 |

质量规则的编辑入口优先放在资产详情和质量工作台；检测记录、异常处置各有明确页签。规则只有一份定义，其他入口只是过滤视图。菜单更名保留旧 URL 重定向，不能让收藏链接失效。

体验验收标准：

- 1366×768、1440×900、1920×1080 三档桌面回归；除宽表格／SQL 编辑区域外，不出现页面级横向滚动。
- 指标卡只保留当前页面决策需要的 3～5 项，详情和低频指标折叠；不在每个模块重复铺满大卡片。
- 固定页头、骨架与实际内容的主要高度；后台刷新保留旧数据，不先清空列表；失败显示错误与最后更新时间。
- 筛选、分页、业务日期、页签进入 URL 或可恢复状态；详情返回列表、刷新、前进后退均不丢失。
- SQL 草稿、参数和结果上下文保留；未保存离开有提示；避免统计轮询触发编辑器或整页重挂载。
- 普通编辑用紧凑弹框／抽屉，建议宽度 560～720 px；复杂任务采用页面式向导，高级参数折叠。
- 提示文字、代码地址、占位符和错误状态有明确视觉层次；浅底深字，深底浅字，无数据不使用成功绿。
- UI 测试覆盖稳定布局、加载、无权限、空态、依赖离线和大列表，不以一次生产构建代替视觉验收。

## 9. 分阶段排期

估算前提：2 名后端、1 名前端，QA／运维分别至少半投入，有可反复重建的真实 Flink／Paimon／Doris 验收环境。建议 **8 个双周迭代＋2～4 周集成缓冲，约 18～20 周**。这是范围级估算，不是已承诺日期；人员、试点规模和 HA 要求未确定，前两周后需重新估算。Beta 不挤占 GA 的安全和回归预算。

| 阶段 | 建议迭代 | 重点与可演示结果 | 出口条件 |
|---|---|---|---|
| A：校准与止漏 | Sprint 1 | 能力实测清单、R01／R04／R06 等高风险回归与修复；冻结 UI 规范 | 当前阻塞有可重复失败用例和修复证据；兼容环境可运行 |
| B：发布与交付 | Sprint 2～3 | 发布包、部署修订、运行 attempt、窗口产出、依赖绑定与质量阻断 | 修改草稿／规则／产出不影响在途实例；新补数不误用旧批次 |
| C：资产与复用 | Sprint 4～5 | 统一资产详情、Schema 风险、普通 View、导航与关键页面改版 | 从资产到源任务、检测、查询、消费的链路贯通；View 权限通过 |
| D：运营与消费 | Sprint 6～7 | 维护／伸缩闭环、生命周期策略、质量和 SLA、API 发布隔离 | 数据不可用可解释且可恢复；维护和伸缩有终态；线上定义不随草稿漂移 |
| E：候选发布 | Sprint 8 | PostgreSQL 兼容补齐、升级迁移、故障恢复、跨模块与 UI 回归 | GA 清单全通过；实验功能默认关闭；明确部署支持范围 |
| 发布缓冲 | 2～4 周 | 试点修正、性能调优、文档和安装验收 | 无未关闭 P0；试点签收与发布说明完成 |

若只能投入 1 名全栈，建议切为 2.0 核心版（A＋B＋关键 UI＋验收）、2.1 资产与 View、2.2 生命周期与物化；不能沿用上述排期还维持全部范围。

## 10. GA 验收与度量

### 10.1 必须通过的场景

- MySQL 和 PostgreSQL：insert／update／delete、重启续传、源端中断、Schema 新增／破坏性变更；校验最终数据而不只看 Job 状态。
- 发布一致性：实例创建后修改 SQL、依赖、产出和规则，实例仍使用固定契约；记录实际执行版本及配置指纹。
- 交付一致性：上游计算成功但质量失败，下游数据依赖不放行；检查成功后可恢复；重复完成回调不重复产出。
- 补数：旧成功批次存在时，新批次仍按选定策略执行；同窗口重试不会无意重复写入，所选写入模式需证明可安全重放。
- 权限：两个互斥数据范围角色覆盖资产、血缘、搜索、任务、检测记录、报表、View、API 管理／调用／导出；撤权和跨对象 ID 请求必须被拒绝。
- 维护：CALL 成功、失败、超时、Gateway 中断均有终态或明确待协调状态；受保护数据不会因批量策略被误删。
- 伸缩：资源充足与不足、并发修改、Job 已变更、调度恢复失败均有明确结果；校验恢复后的数据和 Checkpoint。
- 发布消费：修改 API 草稿不改变线上 SQL 或结果契约；发布后可查版本；禁止无授权的破坏性兼容变更。
- 升级与恢复：历史版本、运行实例、数据范围和 Paimon 定位可核对；停止调度／备份／恢复步骤可执行。
- UI：三档屏幕、快慢网络、后台刷新、浏览器返回、未保存草稿、依赖离线；无可复现的整页跳动或误显示健康。

### 10.2 生产支持范围单独声明

最低 GA 提供经过恢复演练的单控制面部署。双后端副本只能在调度互斥、执行器归属、全局额度、跨副本查询取消和告警去重通过故障测试后标为支持；未通过时明确为未认证，而非只把副本数调成 2。生产配置不得在每次启动时无条件初始化调度库。

默认沿用仓库当前 Flink 2.2.1／Paimon 2.0.0／Doris 4.1.3 组合作为待验收基线，不在产品改版时顺带全面升级引擎。验收记录镜像 digest、Connector、SQL Gateway、Catalog 和共享存储配置；官方文档能力不替代实际组合测试。

### 10.3 建议指标（目标，不是当前成绩）

| 指标 | 建议验收方式 |
|---|---|
| 发布可追溯率 | 新实例／持续部署 100% 关联不可变版本与配置引用 |
| 错误交付阻断 | 门禁失败、无规则、检测引擎失败三类严格策略用例中，下游误放行数为 0 |
| 异步操作可解释性 | 运维操作均可查询受理、进展与终态；无法确认必须显示 unknown／待协调 |
| 权限一致性 | 跨模块权限矩阵负向用例全部通过，未知 SQL 方言不降级放行 |
| 页面可用性 | 标准桌面无页面级横向溢出，筛选／编辑上下文不因刷新或往返丢失 |
| 试点稳定性 | 建议连续 7 天真实链路观察并执行故障演练；不以七天结果直接承诺全年可用性 |
| 性能与容量 | Sprint 1 固定任务量、表量、规则量、SQL／API 并发和数据量，再确定 P95、调度延迟及恢复目标；禁止脱离规模报统一指标 |

统一产品指标优先用“按时且通过质量门禁的交付比例”；可计算为满足截止时间与契约的交付数／应交付数。实时资产使用约定新鲜度达标率，不把常驻任务套入按日成功率。综合健康分仅辅助导航。

## 11. 升级与回退策略

1. 先建立兼容映射：旧 taskId／表 ID 保留，新增 assetId、发布契约与 operationId；旧 API 暂时可用。
2. 对历史实例的版本来源做可信度标记。V19 曾按最新版本回填历史实例，无法据此证明旧运行确实使用那一版；标为 legacy-inferred，不伪装精确追溯。
3. 历史 success 不自动升级成“质量已验收”；没有检测证据的产出标记未验证，不编造历史通过记录。
4. 管理库采用先扩展字段／表、兼容读写，再迁移引用的方式；GA 迁移不得自动搬 Warehouse、重写业务表或删除快照。
5. 上线前备份管理库及 Catalog，按一致恢复方案保护 Warehouse 和 Flink 状态；明确这些组件备份的一致性边界。
6. 在隔离环境演练旧版本升级和应用回退；回退前停调度与新提交，并核对在途 Job。不可逆数据操作不能靠回退前端／后端镜像恢复。

## 12. 范围控制与待确认决策

2.0 暂缓：Doris 异步物化视图 GA、列级血缘与脱敏平台、指标语义层、Kafka／文件新接入、通用审批引擎、多租户与跨湖仓调度、基于 AI 的自动 SQL 变更。

可以先做发布前检查清单、变更理由和高风险二次确认；通用多级审批另排。开发／生产可先独立部署，采用脱敏配置映射，不为了环境隔离引入完整租户系统。

进入开发前需确认的少量决策及当前建议：

| 决策 | 当前建议 | 会影响什么 |
|---|---|---|
| 第一试点 | 一个订单主题，兼顾持续 CDC 与按日交付 | 样例数据、验收范围、功能裁剪 |
| 首个生产部署 | 保留 Standalone 验收；Kubernetes 为增强验证环境 | 伸缩、HA 和运维投入 |
| 原生物化优先级 | 普通 View GA；Flink 物化 Beta；Doris MV 后移 | 引擎兼容成本与大版本交付周期 |
| 数据质量隔离等级 | 默认阻断受治理交付；强隔离作为明确声明的能力 | 暂存产出、快照固定、存储成本 |
| 团队投入与规模 | 按第 9 节估算，Sprint 1 后校准 | 是否拆分 2.0／2.1、具体发布时间 |

在以上决策没有变化时，可直接按 V2-01 → V2-02 → V2-03 开始准备迭代。本次仅形成规划与文档校准，功能开发、迁移和部署另行进入执行阶段。
