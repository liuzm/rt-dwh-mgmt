## 4. 关键契约先确定

以下是待实现的设计约束，首个相关子包中补充接口、数据模型及迁移设计后落代码，避免各模块独立解释同一状态。

### 4.1 API 发布和消费

API 管理对象、发布版本、线上指针分离。调用开始时固定实际版本，发布采用并发版本校验和原子指针切换；回退属于重新校验后的发布动作。发布快照保存 SQL、类型化参数、结果列、声明依赖和运行约束，日志记录该版本及实际执行身份。

历史已发布定义迁移为“迁移时捕获的版本”，不能补造过去的发布内容和时间。迁移前保持服务可核对，迁移后编辑进入草稿。报表在新增消费契约时同样固定每次运行使用的定义和策略，避免定时实例受编辑中的配置影响。

消费策略至少区分“读取当前数据”和“校验指定窗口可用产出后读取”。后者必须在发布时验证所有相关依赖可完整识别、日窗口可由类型化参数或固定调度上下文确定；无法证明映射时拒绝启用严格策略。接受有效豁免单独配置。

首期门禁证明的是所声明交付条件满足。若仍读取会变化的物理表，只能记录“当前数据＋所校验的产出证据”，不能声称返回值来自指定 productionId 的物理快照。不可变历史数据消费由后续快照子包解决。

### 4.2 SLA 与指标

SLA 依据已发布的产出和调度契约生成“应交窗口”，保存截止时间、时区和宽限期。即使调度器没创建实例，也有对象可以判断缺交。初期只覆盖日窗口；补数是否计入业务 SLA 显式设置，不能把所有补数自动加入分母。

迟到和恢复保存为事件，重复协调不重复创建。到达截止时间仍 checking、blocked 或缺产出，均不能算按时交付。恢复依据真实交付证据，重检时间不能冒充原始产出时间。

“按时且通过率”分母为统计区间内已到截止时间、按冻结契约应交的窗口；分子为截止前产出可用且强制质量检查通过的窗口。无规则／无需检查、豁免和取消分别展示，不计作质量通过；没有可统计窗口时显示无数据。调度停用、节假日或计划排除需保存生效时间和理由，不能删除已发生的违约。

### 4.3 质量处置和豁免

问题处置状态、检测结果、交付决定分开保存。确认或分派不改变质量结论；批准豁免也保留失败证据。豁免精确限定规则版本、产出及窗口，并记录有效期和审计。

到期／撤销后，尚未开始的消费和下游提交重新校验。已经运行或已经读取的数据不自动撤回，需显示受影响实例和消费记录。通知通过持久化待发送记录与重试状态跟踪；外部渠道无法保证严格只发一次时，保留去重标识及实际发送尝试，不虚构“恰好一次”承诺。

### 4.4 运维和资产演进

继续使用“意图先持久化、外部提交、观测协调”的流程。绑定操作发生时的环境定位，凭证继续使用可轮换引用；环境修改后仍能核对旧操作。人工接管需记录证据、执行身份和原因，无法确认外部结果时不得直接允许重复提交。

资产 UUID 保持逻辑身份，新增物理观测／重绑定事件。View 和表结构变更根据可解析的消费关系评估；未解析依赖显示未知。迁移先创建可验证的新契约、逐个切换消费方，再处理旧对象，避免以一次原地 ALTER 承诺完整兼容。

## 7. 验收、迁移与发布要求

### 统一验收样例

继续使用隔离的订单主题样例：MySQL／PostgreSQL → ODS → DWD → ADS → 普通 View → SQL／报表／API。对指定日窗口注入缺失、重复、迟到、引擎中断和权限撤销，校验实际数据、执行版本、质量证据及用户可见状态。

| 验收面 | 必测场景 | 必须留存的证据 |
| --- | --- | --- |
| 发布与消费 | 并发修改、发布失败、版本切换中调用、回退、撤权、结果列破坏性变化、历史迁移 | 发布版本、调用实际版本、权限结果、产出／窗口映射及返回数据 |
| SLA 与质量 | 缺实例、边界时刻、跨时区、宽限期、规则停用、引擎错误、补数、重复协调、过期豁免、晚恢复 | 应交窗口、冻结策略、原检测、事件和处置历史；指标可复算 |
| 运维及伸缩 | 提交前后进程退出、响应丢失、旧端点不可达、重复接管、资源不足和并发修改 | 操作意图、句柄／Job ID、协调记录、结果证据；恢复后的数据及 Checkpoint |
| 资产与维护 | 同名重建、改名、复杂类型变化、依赖无法解析、View 漂移、引用保护、清理预览及恢复 | Schema／身份修订、影响清单、迁移和保护决策、真实恢复结果 |
| 权限 | 两个互斥范围账号、管理员、自定义角色；直接 ID、搜索、血缘、质量历史／备注／样本、API、报表、下载和撤权 | 正向及负向结果；无元数据、SQL、错误详情或链接越权 |
| 部署与升级 | 全新安装、从 V27 升级、停止／恢复调度、备份恢复、共享存储、单控制面 Helm 实装 | 迁移前后对象数量及关键关联、镜像／配置指纹、恢复步骤和执行日志 |
| 体验与性能 | 1366×768、1440×900、1920×1080；慢网络、刷新、返回、草稿、空态；固定负载及队列超限 | 页面记录、性能环境／数据集、延迟分布、资源占用及异常结果 |

在 M0 固定任务量、表量、规则量、数据量、SQL／API 并发和查询类型，记录当前基线，再确定验收阈值。目标在负载测试前登记，不能测试后调整标准使其通过；查询、质量和引擎写入分别测量。试点建议连续观察 7 天，并执行计划内故障演练。

复用现有 `smoke-cdc-paimon-doris.sh`、`smoke-release-contract.py`、`smoke-workflow-delivery.py`、`smoke-control-plane.py`、`smoke-asset-contract.py`、`smoke-managed-views.py`、`smoke-quality-windows.py`。新增 API 发布、SLA 处置、PostgreSQL 和恢复场景时，明确哪些是真实引擎执行、哪些使用模拟回调或时间注入。现有 216 个后端 service／controller 用例是已记录基线，不把用例数量作为新的验收目标。

### 数据迁移与回退

1. 每个需要改表的子包提供 Flyway 增量迁移，编号按实施时现有最大版本递增，不预先占用或修改已执行的 V27。
2. 新增记录和字段先兼容读取，再迁移和切换写入；历史信息不足时明确标记未知／迁移捕获，不推断虚假的发布版本或资产身份。
3. 本地执行迁移前备份管理库，测试数据使用专用名称和精确 ID 清理。不得清空共用库或 Warehouse 来使验收通过。
4. 发布前写明旧程序是否兼容新 Schema。无法直接回滚时，采用停调度、备份恢复或前向修复，并校对期间外部作业及数据；仅恢复管理库不等于撤销引擎写入。
5. 每个子包同步更新实现说明、接口及操作文档、权限回归和真实环境证据。通过代码测试后进入本地 Docker 验收，完成阶段出口后才进入候选发布。

## 8. 下一步可直接实施的顺序

首个双周迭代的目标是完成 V2-10A、V2-09A 首个完整链路，并交付 V2-06A 的故障用例与恢复设计；V2-06A 全量预计在 M1 后半段完成。逐项实施时按以下顺序推进：

| 顺序 | 任务 | 可审查结果 |
| --- | --- | --- |
| 1 | 校准入口和基线 | 物化等未认证场景标记、环境清单、回归与性能基线、剩余任务状态表 |
| 2 | API 发布数据模型与迁移 | 草稿／不可变版本／线上指针设计、旧服务迁移、并发版本校验 |

| 5 | 运维恢复和人工接管（当前） | 存储维护子包已通过真实故障演练；继续补持续部署和周期 attempt 的原端点、Session／Operation 持久化、重启续查、清理重试与受控接管，再进入质量契约 |
